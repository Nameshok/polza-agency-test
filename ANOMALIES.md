# ANOMALIES.md — что не так с данными и как я это нашёл

Разбор `review.csv` (207 строк данных) и основной выгрузки `page_001…020.json` (1000 записей),
одиннадцать разделов.
Порядок — по важности, а не по номеру строки. У каждого пункта указано, **как обнаружено**:
все находки воспроизводятся либо запуском загрузчика (`npm run load:all`), либо SQL-запросом,
который приведён рядом.

Метод в целом: я не читал файлы глазами. Загрузчик сначала кладёт каждую строку в
`import_rows` — как пришла, с номером строки файла — и ставит статус плюс список замечаний.
Дальше все вопросы к данным превращаются в SQL по этой таблице. Поэтому находки
пересчитываются в любой момент, а не существуют только в этом тексте.

---

## 1. Шесть «новых» компаний почти наверняка уже есть в базе под другими id

Сразу оговорюсь про статус: это **кандидаты в дубли с высокой уверенностью**, а не
доказанный факт. Совпадение полей — очень сильный довод, но окончательное «это одна
компания» должен подтвердить человек, поэтому загрузчик их не склеивает (см. ниже).
Практический риск: если такие записи уедут в рассылку неразобранными, шесть компаний
получат письмо дважды.

| строка CSV | id в CSV | название в CSV | уже есть как | название в базе |
|---|---|---|---|---|
| 25 | `c_900008` | АО Флагман Лаб | `c_000229` | АО «Флагман Лаб» |
| 75 | `c_900009` | АО Сокол | `c_000656` | АО «Сокол» |
| 115 | `c_900010` | Модуль Строй | `c_000571` | «Модуль Строй» |
| 126 | `c_900011` | АО Сокол Лаб | `c_000957` | АО «Сокол Лаб» |
| 139 | `c_900007` | Прайм Плюс | `c_000642` | «Прайм Плюс» |
| 177 | `c_900006` | АО Орион Групп | `c_000738` | АО «Орион Групп» |

У всех шести совпадают город, адрес, сайт, рейтинг и число отзывов; телефон совпадает
у пяти, а у шестой (`c_900006`) его нет ни в CSV, ни в уже загруженной записи. Отличается
только название, с которого сняты кавычки, и id: он из диапазона `c_9000xx`, которого
в основной выгрузке нет вообще (там строго `c_000001`…`c_001000`, а свежие записи идут
как `c_001001`…`c_001190`).

**Как обнаружено.** Дедупликация по `id` их не видит, по названию — тоже. Нашлись сверкой
телефонов: у пяти из шести телефон уже есть в базе. Шестой (`c_900006`) телефона не имеет —
он попался по паре «город + адрес» плюс совпадение названия без кавычек и правовой формы.
Это и стало правилом в загрузчике (`findDuplicates` в `scripts/lib/store.ts`):

```sql
-- те же строки прямо из базы, после загрузки
SELECT external_id, duplicate_of, match_reason, confidence,
       details->>'new_name' AS new_name, details->>'existing_name' AS existing_name
  FROM duplicate_candidates WHERE confidence = 'high' ORDER BY external_id;
```

**Что сделал.** В `companies` не пустил — статус `quarantined` в `import_rows` плюс запись
в `duplicate_candidates`. Автоматически склеивать не стал: решение «это одна компания»
должно быть подтверждено человеком, а не загрузчиком.

Отдельно нашлись ещё **5 пар со средней уверенностью** (`confidence = 'medium'`): разные
названия по одному адресу — `c_001047`/`c_000606`, `c_001162`/`c_000427`, `c_001176`/`c_000168`,
`c_001178`/`c_000159`, `c_001181`/`c_000596`. Загружены как обычные компании, но помечены
на проверку.

Тут стоит сказать, почему они именно «средние», а не дубли. Адресное пространство выгрузки
маленькое: **20 городов × 18 названий улиц × номера домов до 120**, у 420 записей есть ещё
и офис. Если бы адреса раздавались равномерно и независимо, случайных совпадений пары
«город + дом» на 1183 записях ожидалось бы порядка пяти-семи — найдено пять. Оговорюсь,
что это прикидка, а не доказательство: равномерность генерации я проверить не могу,
и отличить случайную коллизию от двух организаций в одном здании по этим данным нельзя
в принципе. Именно поэтому пары помечены на проверку, а не склеены. Практический вывод
тот же, что и по сайту: **совпадение адреса на этой базе ничего не доказывает.**

## 2. В основной выгрузке 6 повторяющихся id и 6 отсутствующих

В 20 файлах ровно 1000 записей и `total: 1000` — арифметика сходится, и на этом обычно
останавливаются. Но **уникальных id только 994**.

- Продублированы: `c_000224`, `c_000254`, `c_000263`, `c_000285`, `c_000367`, `c_000453`
  (записи побайтово идентичны).
- Пропали: `c_000566`, `c_000646`, `c_000687`, `c_000723`, `c_000800`, `c_000848`.

Это факт по файлам. Причину по ним доказать нельзя, но картина характерна для выборки
по `LIMIT/OFFSET` без стабильной сортировки: пока читаются страницы, порядок меняется,
часть строк попадает в две страницы, часть не попадает ни в одну. Подтвердить или
опровергнуть это можно только логами или запросом на стороне API — у меня их нет,
поэтому оставляю как гипотезу.

**Как обнаружено.** Счётчик уникальных id против общего числа записей и поиск дыр
в числовой части id — печатается при каждом запуске `npm run load:json`.

**Что сделал.** Дубли не создают вторых записей (upsert по `external_id`, статус
`duplicate`). Шесть отсутствующих компаний из этих файлов восстановить нечем — их там
просто нет. Если выгрузку придётся повторять, для полноты состава понадобится стабильная
сортировка, например по `id`: иначе на каждой перекачке будет расходиться примерно
0,6 % записей.

## 3. Съехавшие колонки — строка выглядит валидной, но данные не на своих местах

Строка 37, `c_001015`: в `category` лежит `Пермь`, в `city` — `ул. Советская, д. 89, офис 43`,
`address` пустой. CSV при этом синтаксически корректен, и любой `Import-Csv` / `csv.DictReader`
загрузит это молча.

**Как обнаружено.** Сверка значений со справочником: город, которого нет среди 20 городов
основной выгрузки, и при этом похожий на адрес (`^ул\.` или `, д. N`). Такой строке
присваивается замечание `city_looks_like_address`.

**Что сделал.** В карантин (`broken_row_structure`). Считать компанию находящейся
в городе «ул. Советская» нельзя, а угадывать, что там было на самом деле, — тем более.
Заметно, что без этого правила запрос «доля компаний с сайтом по категориям»
выдавал категорию **«Пермь»** — то есть одна битая строка портит отчёт.

## 4. Битая кодировка в двух строках

- строка 113, `c_001008`: `name` = `РћРћРћ В«Р—Р°СЂСЏ РўРµС…В»`, `city` = `РњРѕСЃРєРІР°`
- строка 155, `c_001128`: `name` = `РћРћРћ В«РўРµРјРї РњРµРґРёР°В»`, `city` = `РЎР°РЅРєС‚-РџРµС‚РµСЂР±СѓСЂРі`

Сам файл — валидный UTF-8, то есть побилось не при передаче, а раньше: UTF-8 прочитали
как windows-1251 и сохранили результат.

**Как обнаружено.** Признак — заглавная `Р`/`С`/`В`/`Т`, за которой без пробела идёт символ
из верхней половины cp1251 (`Рћ`, `В«`, `Сѓ`). В живом русском тексте таких пар не бывает.

**Что сделал.** Починил обратным преобразованием (`cp1251 → utf-8`), но с двумя
предохранителями: ремонт применяется только если результат стал «чище» исходника,
и только если строка полностью представима в cp1251. Исходное значение осталось в
`import_rows.raw`, замечания — `name_mojibake_repaired`, `city_mojibake_repaired`.
После ремонта «ООО «Заря Тех»» и «ООО «Темп Медиа»» нормально ищутся на странице
`/companies` — это и была проверка, что ремонт настоящий.

## 5. Один город в шести написаниях

| строка | как записано | что это |
|---|---|---|
| 22 | `Санкат-Петербург` | опечатка |
| 113 | `РњРѕСЃРєРІР°` | битая кодировка (см. п. 4) |
| 127 | `Moscow` | латиница |
| 148 | `Москва ` | хвостовой пробел |
| 155 | `РЎР°РЅРєС‚-РџРµС‚РµСЂР±СѓСЂРі` | битая кодировка |
| 166 | `москва` | нижний регистр |

Без нормализации в фильтре по городу появилось бы шесть лишних «городов», а средний
рейтинг по Москве считался бы по неполной выборке.

**Как обнаружено.** Сравнение со справочником городов, собранным из основной выгрузки API
(она принята за доверенный источник — 20 городов). Всё, что не совпало точно: сначала
регистр, потом алиасы и транслит, потом опечатка в 1–2 правки (расстояние Левенштейна).

**Что сделал.** В `companies` два поля: `city` — как в источнике, `city_key` — канонический
город. Все агрегаты и фильтр работают по `city_key`. Замечания: `city_case_mismatch`,
`city_alias_or_translit`, `city_typo_fixed`, `city_whitespace`.
**Важно:** если город не опознан ни одним способом, `city_key` остаётся `NULL` —
выдумывать город загрузчик не имеет права.

## 6. Числа, которых не бывает

| строка | id | поле | значение | что сделал |
|---|---|---|---|---|
| 197 | `c_001186` | `rating` | `7.2` | вне шкалы 0–5 → `NULL`, замечание `rating_out_of_range` |
| 96 | `c_001122` | `rating` | `-3` | то же |
| 9 | `c_001083` | `rating` | `N/A` | `NULL`, `rating_not_a_number` |
| 14 | `c_001010` | `rating` | `4,5` | десятичная запятая → `4.5`, `rating_decimal_comma` |
| 61 | `c_001116` | `reviews_count` | `-10` | `NULL`, `reviews_negative` |
| 98 | `c_001079` | `reviews_count` | `45.5` | `46`, `reviews_not_integer` |
| 200 | `c_001187` | `reviews_count` | `много` | `NULL`, `reviews_not_a_number` |

Значения вне диапазона я **не подтягиваю к границе** (7.2 не превращается в 5.0):
такое значение некорректно целиком, и честнее записать «рейтинг неизвестен», чем
придумать за источник правдоподобное число.

Единственное место, где я всё же меняю значение, а не обнуляю его, — `45.5` отзыва → `46`,
и разницу стоит проговорить, иначе выглядит как непоследовательность. `7.2` на шкале 0–5
— это не рейтинг вообще, подтягивание к 5.0 сочинило бы величину, которой в источнике нет.
А `45.5` — это счётчик, пришедший в дробном виде: сама величина осмысленна, дробной
она быть не может, и округление сохраняет её, а не выдумывает. Строка при этом всё равно
помечена `reviews_not_integer`, то есть человек её увидит. Если предпочтительнее строгий
вариант — обнулять и такое, — это одна строка в `parseReviewsCount`.

Отдельно про порядок проверок в этом же месте: отрицательное значение отсекается **до**
округления. Обратный порядок был бы тихой миной — `-10.5` округлилось бы в `-10`
и упёрлось в `CHECK (reviews_count >= 0)`, уронив весь прогон загрузки. В данных задания
такого значения нет, поэтому проявилось бы это только на следующей выгрузке; закрыто тестом.

Отдельно и важно: **неизвестное значение — это `NULL`, а не `0`.** Это касается и рейтинга
(79 записей из API и 21 из CSV, итого 100 компаний из 1183), и числа отзывов.
Если превратить их в нули, средний рейтинг
по городу поедет вниз на десятые доли, и запрос №2 из задания начнёт врать; а «0 отзывов»
вместо «неизвестно» — это утверждение, которого в данных нет.

У `reviews_count` есть второе следствие, из-за которого я переделал обработку этого поля. Загрузчик
не затирает непустое старое значение пустым новым. Пока «неизвестно» кодировалось нулём,
это правило на `reviews_count` не работало: следующая выгрузка с мусором в этом поле
записала бы существующей компании ноль отзывов и стёрла корректный счётчик. Теперь там
`NULL`, и правило действует. Проверяется скриптом `npm run test:db` — он берёт живую запись,
пробует обновить её обеднённой версией и убеждается, что ничего не потерялось
(всё внутри транзакции, которая откатывается).

В схеме стоят ограничения `CHECK (rating BETWEEN 0 AND 5)` и `CHECK (reviews_count >= 0)`,
так что мусор физически не пройдёт в таблицу — это тоже проверяется в `test:db`.

**Как обнаружено.** Валидация типа и диапазона при загрузке; сводка — в
`npm run report`, раздел «Замечания по полям».

### Один домен у нескольких компаний — 7 случаев

Начал с бросающегося в глаза `https://shared-site.ru` (`c_001135` «Дельта Про», Москва
и `c_001088` «Вертикаль Тех», Краснодар), а когда написал под это запрос, нашлось ещё шесть:

| домен | у каких компаний он указан в выгрузке |
|---|---|
| `shared-site.ru` | `c_001088` (Краснодар), `c_001135` (Москва) |
| `ip-73.ru` | `c_000631` (Нижний Новгород), `c_001124` (Нижний Новгород) |
| `ip-445.ru` | `c_000025` (Тюмень), `c_001120` (Воронеж) |
| `ip-585.ru` | `c_000796` (Москва), `c_000835` (Самара) |
| `ip-715.ru` | `c_000219` (Тюмень), `c_000829` (Москва) |
| `ip-756.ru` | `c_000135` (Нижний Новгород), `c_000694` (Санкт-Петербург) |
| `ip-788.ru` | `c_000782` (Челябинск), `c_000869` (Ростов-на-Дону) |

Шесть из семи — домены вида `ip-NNN.ru`, то есть похоже на коллизию в генераторе адресов
на стороне источника, а не на настоящий общий сайт. Компании при этом разные: разные
названия, города, телефоны и категории. Практический вывод для аутрича: **сайт нельзя
считать уникальным ключом компании** — ни для дедупликации, ни для «одна компания = одно письмо».

**Как обнаружено, и почему сначала неправильно.** Первый запрос группировал по колонке
`site` целиком и нашёл шесть пар. Седьмая (`ip-715.ru`) не находилась, потому что у одной
компании домен записан как `https://ip-715.ru`, а у другой — `http://ip-715.ru`: для
`GROUP BY site` это две разные строки. В выгрузке 748 сайтов через `https` и 142 через
`http`, так что промах был системным, а не случайным. Всплыло при выводе адресов из доменов
(п. 10) — там схема отбрасывается, и пара сошлась. Запрос исправлен: группировка идёт
по нормализованному домену, он же теперь в `npm run report`:

```sql
SELECT lower(regexp_replace(regexp_replace(site, '^https?://', ''), '^www\.', '')) AS domain,
       count(*) AS companies,
       string_agg(external_id || ' (' || coalesce(city_key, '?') || ')', ', ') AS who
  FROM companies
 WHERE site IS NOT NULL
 GROUP BY 1
HAVING count(*) > 1
 ORDER BY count(*) DESC, 1;
```

Урок из этого шире самой находки: **сравнивать надо нормализованное значение, а не то,
как его записал источник.** Ровно та же ошибка возможна на городе и на телефоне, и именно
поэтому в схеме рядом с `city` лежит `city_key`, а рядом с `phone` — `phone_e164`.

## 9. Рейтинг и отзывы не сходятся между собой

- **81 запись** имеет отзывы, но не имеет рейтинга (`rating_missing_with_reviews`).
- **7 записей** наоборот: рейтинг есть, а отзывов ноль (`rating_without_reviews`).

Ни то, ни другое я не «исправлял»: подставить рейтинг нечем, а обнулять отзывы —
значит терять факт. Это вопрос к источнику данных, и он должен быть виден, а не замазан.

**Как обнаружено.** Проверка согласованности полей при загрузке (не диапазон каждого
по отдельности, а связь между ними).

## 10. Поля email нет, а домены в выгрузке в основном не существуют

В критериях тестового задания: «Качество базы — реальные, валидные email — **высокий** вес».
В данных email нет ни в JSON, ни в CSV: символ `@` не встречается во всех 21 файле выгрузки
ни разу, и в описании полей в самом ТЗ он тоже не упомянут.

Останавливаться на этом я не стал. Единственная зацепка для адресов — домен сайта,
поэтому я собрал кандидатов из доменов и прогнал их по шести этапам из вашего курса
(`npm run emails`): опечатки в домене → синтаксис → ролевые ящики → одноразовые домены →
MX → SMTP. Результат:

```
Компаний с сайтом:            890
Уникальных доменов:           883   (7 доменов используются дважды: 14 компаний)
Кандидатов в адреса:         2670   (info@, sales@, contact@ на каждую компанию)
Отсеяно до обращения к сети:    0
  доменов существует:           6 из 883
  доменов с MX-записью:         3 из 883

valid 0 · quarantined 0 · unknown 9 · rejected 2661   (все 2661 — на этапе MX)
```

**Валидных — ноль, и причина не в методе проверки. 877 доменов из 883 не существуют
в DNS.** Здесь важно сказать ровно то, что доказано, не больше:

- **884 компании** сидят на этих несуществующих доменах. Для них недоставим **любой**
  адрес на их собственном домене — не только угаданные `info@`/`sales@`/`contact@`.
  Это следует из отсутствия домена и от способа угадывания ящика не зависит.
- **293 компании** вообще без сайта: домена нет, сказать про них по этим данным нечего.
- **6 компаний** на доменах, которые резолвятся. Их 9 адресов остались в статусе
  `unknown`, потому что SMTP-этап выключен, — это «не проверяли», а не «плохие».

Чего эти цифры **не** доказывают: что у самих компаний нет никаких email вообще.
Проверялся домен из выгрузки, а не компания. Вывод корректно звучит так: **для 2661
кандидата отказ не зависит от метода проверки — домена просто нет; оставшиеся 9 требуют
SMTP, который здесь выключен, поэтому они `unknown`, а не «плохие».** Подтверждённых
адресов этот прогон не дал ни одного, и построить из этой выгрузки базу для рассылки
нельзя.

**Как обнаружено.** `dns.resolveMx`, а при отсутствии MX — `dns.resolve4` по каждому
уникальному домену. Различать эти два случая обязательно: «домена нет» и «домен есть,
почты нет» — разные причины отказа и разный совет по базе.

### Шесть доменов всё-таки живые, и это ловушка, а не удача

| домен | MX |
|---|---|
| `expert-56.ru` | нет |
| `ip-1.ru` | нет |
| `ip-55.ru` | `mx1.timeweb.ru` |
| `ip-68.ru` | `mail.ip-68.ru` |
| `nord-2.ru` | нет |
| `prime-110.com` | `mx01.lolipop.jp` |

У всех шести маленький номер в имени (`1`, `2`, `55`, `56`, `68`, `110`) — то есть
короткое имя, которое с большой вероятностью уже занято кем-то настоящим. Три из них
принимают почту на серверах хостеров (`timeweb.ru`, `lolipop.jp`). Что именно за этими
доменами и связаны ли они с компаниями из выгрузки, я не проверял и утверждать не могу:
DNS доказывает только существование записи. Но именно поэтому **обогащение без проверки
владельца опасно**: три живых почтовых сервера примут попытку доставки, и уйдёт она
с вашего домена и вашей репутацией — при том, что принадлежность адресата не подтверждена
ничем.

Поэтому в схеме у каждого адреса стоит `source = 'derived_from_site'`: выведенный адрес
не должен ни при каких условиях смешаться с полученным из источника. Ни один адрес
в этом прогоне не получил статус `valid`.

**Что сделал по самому пайплайну.** Ролевой ящик (`info@`, `sales@`) не отбрасывается
на третьем этапе, а помечается и идёт дальше: иначе про домен так и не узнаешь,
существует ли он. Но `valid` ролевой адрес получить не может — максимум карантин.
Это отдельно закреплено тестом, потому что ошибка здесь тихая.

Две оговорки, которые важно проговорить заранее, потому что они влияют на ожидания
от цифр. Первая: SMTP-проверка не доказывает, что ящик живой — catch-all-домены отвечают
согласием на любой адрес, и такие результаты надо помечать отдельно, а не считать
валидными. Вторая: ответ `unknown` не означает «адрес плохой», и списывать такие адреса
нельзя; их надо гонять пачками с задержкой и перепроверять, иначе база будет выглядеть
хуже, чем она есть. По этой же причине SMTP-этап выключен по умолчанию: живая проверка
с произвольного IP портит репутацию отправителя, её делают с выделенного адреса.

Если настоящая выгрузка с email существует — пришлите, импорт и поадресные статусы уже
написаны, поменяется только источник адресов.

## 11. Междугородний код телефона не связан с городом компании

Телефон есть у 1052 компаний с известным городом. Из них 347 мобильных (`9xx`) —
географию не несут в принципе. Остаётся 705 городских номеров, и с ними две проблемы.

**Первая: в выгрузке всего восемь городских кодов на двадцать городов.**

| код | чей | номеров |
|---|---|---|
| `343` | Екатеринбург | 114 |
| `843` | Казань | 103 |
| `863` | Ростов-на-Дону | 94 |
| `383` | Новосибирск | 87 |
| `831` | Нижний Новгород | 85 |
| `499` | Москва | 80 |
| `495` | Москва | 73 |
| `812` | Санкт-Петербург | 69 |

Эти коды покрывают семь городов. У остальных **тринадцати** (Волгоград, Воронеж, Калуга,
Краснодар, Омск, Пермь, Самара, Сочи, Тула, Тюмень, Уфа, Челябинск, Ярославль) своего кода
в данных нет ни разу. То есть **264 компании — 37 % городских номеров — имеют телефон,
который географически не может быть верным**: у компании в Сочи стоит екатеринбургский код,
и никакого другого варианта в выгрузке для неё не предусмотрено.

**Вторая: внутри оставшихся кодов связи тоже нет.** Код совпал с городом компании у 71
номера из 705 — 10,1 %. Если бы код ставился случайно из этих же восьми кодов с их же
частотами, ожидалось бы **9,9 %**. Разница в пределах шума. Та же картина, если считать
только по семи «представимым» городам: наблюдается 16,1 % при ожидании 15,8 %.

Здесь стоит оговориться про метод. Сравнивать надо с теми кодами, которые в данных
действительно есть, а не со справочником всех кодов России: во втором случае база
сравнения получилась бы около 5 %, наблюдаемые 10 % выглядели бы «вдвое лучше случайного»,
и вывод был бы противоположным и неверным. Я на этом сначала и ошибся.

**Как обнаружено.** Первые три цифры номера в E.164 против справочника кодов тех
20 городов, что есть в выгрузке; затем — подсчёт ожидаемой доли совпадений по фактическому
распределению кодов.

**Практический вывод.** Гео-сегментация по коду номера на этой базе даст неверный город
примерно для девяти компаний из десяти, а для тринадцати городов — гарантированно неверный.
Если в CRM регион подтягивается из телефона, на этих данных он будет врать, и обзвон поедет
не по тем часовым поясам. Опираться надо на поле `city` после нормализации (п. 5), а не
на номер.
